# GeneHub Frontend

## Project Overview
React frontend for GeneHub, a multi-tenant genetic inventory system for cattle
breeding operations: sires, customers, liquid-nitrogen tanks and canisters, the
straws stored in them, and medical supplies. Each customer gets a workspace on
its own subdomain, with owner / admin / member roles and Stripe billing.

The repo root `README.md` covers setup and deployment. This file is about how
the frontend code is organised.

## Tech Stack
- React 19, TypeScript, Vite 7
- React Router 7
- Supabase: Postgres (RLS), Auth, Storage, Edge Functions. There is no app
  server; the browser calls Supabase directly, so authorisation is RLS
- TanStack React Query 5 for data fetching and caching
- Recharts for charts
- Vitest + Testing Library for tests (`src/test/`)

## Multi-tenancy in the frontend
- The workspace comes from the JWT. The subdomain only brands the page.
- `src/config/tenant.ts` exports a mutable `tenant` object (name, logo, login
  hint, report footer) and helpers. `App.tsx` fills it with `applyTenant()` from
  the signed-in user's tenant, or before login from the subdomain via the
  `get_tenant_branding` RPC. Read it at render time. Don't hard-code "RCK".
- `tenantSlugFromHostname()` returns `null` for the apex, `www`, `localhost` and
  IPs. In that case `App.tsx` renders only the landing, pricing and legal
  pages. To use the app locally, browse to a host like
  `<workspace-slug>.dev.localhost:5173`.
- The client never sends `tenant_id`. Columns default to `current_tenant_id()`.
- Foreign-key hints in PostgREST embedded selects must name the constraint
  (`employees!activity_log_user_id_fkey`), not the column.

## Architecture Decisions

### React Query
All data fetching and mutations go through React Query.

**QueryClient configuration** (`src/main.tsx`):
```ts
const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 1000 * 60 * 5,  // 5 minutes
      gcTime: 1000 * 60 * 30,    // 30 minutes
      retry: 1,
      refetchOnWindowFocus: false,
    },
  },
});
```

**Query keys** are centralised in `src/constants/queryKeys.ts` as `QUERY_KEYS`.
Use them for both queries and invalidation. Some are functions of an id
(`canisters(tankId)`), and some have a separate base key for invalidating every
parameterised variant (`allMedicalInventoryStats`, `allUsageHistory`).

**Read hooks and the keys they use:**

| Hook | Keys |
|------|------|
| `useSireList` | `sires` |
| `useInventoryList` (Genetic) | `geneticInventory` |
| `useCustomerList` | `customers` |
| `useActivityLogList` | `activityLog` |
| `useTankList` | `tanks`, `canisters(tankId)`, `canisterInventory(canisterId)` |
| `useTankDetails` | `nitrogenFillHistory(tankId)`, `nitrogenConsumptionStats(tankId)` |
| `useInventoryDependencies` | `sires`, `tanks`, `canisters(tankId)` |
| `useCategoryList` (Medical) | `medicalCategories` |
| `useInventoryList` (Medical) | `medicalInventory` (+ `allMedicalInventoryStats` on inline edit) |
| `useUsageLog` | `usageHistory(itemId)` |
| `useDashboard` | `customerCount`, `sireCount`, `geneticInventoryCounts`, `medicalInventoryStats(days)`, `tanks` |
| `useUserSettings` | `userSettings(userId)` |

### Mutations
Two helpers live in `src/hooks/useCRUDMutation.ts`:
- `useCRUDMutation`: wraps create/update/delete with cache invalidation for the
  keys you list, a minimum delay (`MIN_MUTATION_DELAY`) so the loading state
  doesn't flash, consistent error handling, and optional optimistic delete.
- `useSimpleMutation`: the same for mutations that only need a save, with no
  delete. Used for usage logs and restocking.

```ts
const createMutation = useMutation({
  mutationFn: (data) => createSire(data, userId),
  onSuccess: () => {
    queryClient.invalidateQueries({ queryKey: QUERY_KEYS.sires });
    queryClient.invalidateQueries({ queryKey: QUERY_KEYS.sireCount }); // dashboard
  },
});
```

**What each form or mutation hook uses today:**

| Hook | Mutation approach | Also invalidates |
|------|-------------------|------------------|
| `useSireForm` | `useCRUDMutation` | `sireCount` |
| `useCustomerForm` | `useCRUDMutation` | `customerCount`, `customersWithInventory` |
| `useInventoryForm` (Genetic) | `useCRUDMutation` | `geneticInventoryCounts`, `canisters`, `canisterInventory`, `tanks`, `sires` |
| `useCheckinForm` | `useCRUDMutation` | `geneticInventoryCounts`, `canisters`, `canisterInventory`, `tanks` |
| `useInventoryForm` (Medical) | `useCRUDMutation` | `allMedicalInventoryStats` |
| `useCategoryForm` | `useCRUDMutation` | `medicalInventory` |
| `useTankForm`, `useCanisterForm`, `useFillForm` | plain `useMutation` | `tanks` (`canisters` for canisters) |
| `useUsageLog` | `useSimpleMutation` | `allMedicalInventoryStats`, `allUsageHistory`, `medicalInventory` |
| `useInventoryQuantity` | `useMutation` | `geneticInventory`, `geneticInventoryCounts` |
| `useUserSettings` | `useMutation` with an optimistic update | `userSettings(userId)` |
| `useInventoryList` (Medical) | `useMutation` (inline edit) | `allMedicalInventoryStats` |

A mutation that changes something counted on the dashboard must invalidate that
count key too, or the dashboard goes stale for up to five minutes.

### Dynamic queries with `useQueries`
`useTankList` uses `useQueries` to load canisters for whichever tanks are
expanded, and inventory for whichever canisters are expanded, so nothing is
fetched for collapsed rows.

### Pagination
- **Server-side**: Sires, Genetic Inventory and Customers use the shared
  `usePaginatedQuery` hook (`src/hooks/usePaginatedQuery.ts`), which owns page
  state, debounced search (300 ms by default via `useDebounce`) and resetting
  the page when filters change. The API functions are `fetchSiresPaginated`,
  `fetchGeneticInventoryPaginated` and `fetchCustomersPaginated`. Genetic
  inventory search uses the `search_genetic_inventory` RPC, which searches
  across the joined sires, customers and tanks. Customers use `search_customers`.
- **Client-side**: Tanks and Medical Inventory load everything, then paginate
  with `usePagination` inside the page components.
- **Async dropdown**: `AsyncSearchableSelect` fetches sires as the user types
  (`searchSires`) instead of loading every sire up front.

## Database
The app uses PostgREST plus RPC functions for what it can't express:
`search_genetic_inventory`, `search_customers`, `insert_canister_at_position`,
`normalize_canister_positions`, and for workspaces `get_tenant_branding`,
`update_tenant_branding`, `is_slug_available`, `set_member_role`,
`remove_member`. Schema and policies are in `supabase/migrations/`.

## Potential Improvements (Refactoring Opportunities)

### High Priority

**1. Form hook factory.** The form hooks (`useSireForm`, `useCustomerForm`,
both `useInventoryForm`s, `useCategoryForm`, `useTankForm`, `useCanisterForm`,
`useFillForm`, `useCheckinForm`) are built from the same pieces:
`useModalState` + `useConfirmModal` + a mutation + `useFormState` +
`useFormValidation`, with a similar return shape. A generic factory taking a
config object could remove most of the duplication.

**2. Standardise the mutation approach.** `useTankForm`, `useCanisterForm` and
`useFillForm` use plain `useMutation`; the other forms use `useCRUDMutation`.
Move these three over for consistency.

### Medium Priority

**3. `useCanisterForm` delete state.** It keeps its own
`confirmDeleteCanisterState` in `useState` instead of using `useConfirmModal`
like the other forms.

**4. Centralised data sanitisation.** Each form does its own trimming,
empty-string-to-null and number conversion (see the `sanitizedData` block in
`useSireForm`). Shared helpers such as `sanitizeString(val)` and
`toNumberOrNull(val)` would remove the repetition.

**5. Remove the unused `useAsyncOperation` hook.** Only its
`formatErrorMessage` export is imported (by `useCRUDMutation` and the tank,
canister and fill forms); the hook itself is only exercised by its own test.
Move `formatErrorMessage` somewhere shared and delete the hook and its test.
